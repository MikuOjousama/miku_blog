# Miku 网站：Cloudflare Pages 与 .loc.cc 域名部署指南
 
---

## 1. 部署架构总览

本项目有两套彼此独立的网站托管方案：

### 1.1 GitHub Pages 方案（`.isroot.in`）

```text
GitHub 仓库
    │
    ▼
GitHub Pages
    │
    ▼
hatsunemiku.isroot.in

DNS 托管：DNS.he.net
网站托管：GitHub Pages
```

此方案单独记录在《Miku 网站： Github 与 .isroot.in 域名部署指南》中，不属于本文的 Cloudflare Pages 部署流程。

### 1.2 Cloudflare Pages 方案（`.loc.cc`）

```text
GitHub 仓库
    │
    │ Cloudflare Pages 连接仓库并拉取源码
    ▼
Cloudflare Pages 项目
    │
    ├── hatsunemiku.loc.cc
    │
    └── hatsune-miku.loc.cc
```

已确认的关系：

- Cloudflare Pages 项目：连接 GitHub 仓库，拉取源码并构建、部署
- Pages 默认访问地址：`-xxxx.pages.dev`
- 自定义域名一：`hatsunemiku.loc.cc`
- 自定义域名二：`hatsune-miku.loc.cc`
- 两个 `.loc.cc` 域名绑定到同一个 Cloudflare Pages 项目
- `.loc.cc` 域名及 DNS 由域名服务商自己的平台管理
- 当前采用免费服务方案

**重要：** `.loc.cc` 的 DNS 不由 DNS.he.net 管理；`.isroot.in` 才使用 DNS.he.net。Cloudflare Pages 是网站托管和构建平台，不代表域名注册或 DNS 托管也转移到了 Cloudflare。

---

## 2. 部署前需要准备

1. 可以正常访问的 GitHub 账号。
2. 存放网站源码的 GitHub 仓库。
3. Cloudflare 账号。
4. 已注册并能管理 DNS 的两个域名：
   - `hatsunemiku.loc.cc`
   - `hatsune-miku.loc.cc`

建议先确认 GitHub 仓库当前代码可以正常构建，再连接 Cloudflare Pages。

---

## 3. 创建或检查 Cloudflare Pages 项目

### 3.1 连接 GitHub

在 Cloudflare 控制台中进入 **Workers & Pages / Pages**，创建 Pages 项目并选择连接 Git。

操作思路：

1. 选择连接 GitHub。
2. 按提示授权 Cloudflare 访问对应 GitHub 仓库。
3. 选择仓库。
4. 选择生产分支。
5. 进入构建设置。

### 3.2 构建设置

构建设置需要与仓库实际使用的框架和目录结构一致。重点检查：

| 配置项 | 应如何确定 |
|---|---|
| Framework preset | 根据项目实际框架选择；不要仅凭仓库名称推断 |
| Build command | 查看项目原有构建方式、`package.json` 脚本或仓库说明 |
| Build output directory | 以构建工具实际生成目录为准 |
| Root directory | 只有项目源码不在仓库根目录时才需要调整 |
| Environment variables | 仅填写项目构建确实需要的变量 |


### 3.3 保存并首次部署

1. 检查仓库、生产分支和构建设置。
2. 保存并启动首次部署。
3. 在 Pages 项目的部署记录中查看构建日志。
4. 构建成功后，先访问默认地址 `xxxxx.pages.dev`。
5. 确认首页、静态资源、页面跳转和文章内容正常，再配置自定义域名。

---

## 4. 绑定两个 `.loc.cc` 自定义域名

在 Cloudflare Pages 对应项目中进入 **Custom domains（自定义域名）**，分别添加：

- `hatsunemiku.loc.cc`
- `hatsune-miku.loc.cc`

两个域名都应添加到**同一个 Pages 项目**，而不是创建两个不同的 Pages 项目。

### 4.1 DNS 配置原则

`.loc.cc` 域名的 DNS 由域名服务商自己的管理平台负责。添加自定义域名时：

1. 在 Cloudflare Pages 中添加域名。
2. 根据 Cloudflare Pages 显示的验证要求和 DNS 指引，到 `.loc.cc` 服务商的 DNS 管理页面配置记录。
3. 记录类型、目标值、验证记录等，以 Cloudflare 控制台对该域名给出的实时要求为准。
4. 等待 DNS 生效，并在 Pages 自定义域名页面确认域名状态。


### 4.2 两个域名的关系

两个域名都指向同一个 Cloudflare Pages 项目，因此它们提供的是同一项目部署出来的网站内容。

---

## 5. 后续更新与自动部署

Cloudflare Pages 连接 GitHub 后，通常会根据项目配置监测指定分支的提交，并触发构建部署。

日常更新流程：

1. 在本地修改网站源码。
2. 检查修改内容。
3. 提交并推送到 GitHub 仓库。
4. 打开 Cloudflare Pages 项目查看新部署记录。
5. 确认构建成功。
6. 分别访问两个 `.loc.cc` 域名，检查页面是否更新。

如果只是推送了代码，但页面没有更新，先检查部署记录和构建日志，不要立即修改 DNS。

## 6. 常见问题排查

### 6.1 Pages 构建失败

优先检查：

- GitHub 仓库是否有最新提交。
- Pages 项目是否连接了正确仓库和分支。
- Build command 是否与仓库脚本一致。
- 输出目录是否与实际构建产物目录一致。
- 是否缺少必要的环境变量。
- 构建日志中的第一条关键错误。

不要只看最后一行失败提示；从日志中最早出现的错误开始排查。

### 6.2 自定义域名无法访问

按顺序检查：

1. Pages 项目的 Custom domains 中，域名是否已添加。
2. 域名服务商的 DNS 记录是否与 Cloudflare 提示一致。
3. DNS 记录是否有拼写错误或旧记录冲突。
4. DNS 是否已经传播。
5. Pages 域名验证和 HTTPS 证书状态是否正常。

DNS 记录刚修改时，可能需要等待一段时间才能在不同递归 DNS 服务器上看到一致结果。

### 6.3 默认 Pages 地址正常，但 `.loc.cc` 不正常

这通常说明网站构建本身可能没有问题，应优先检查自定义域名绑定、DNS 解析和 HTTPS 证书，而不是先修改网站代码。

### 6.4 页面能打开，但图片或样式丢失

检查：

- 静态资源路径是否使用了正确的相对路径或根路径。
- 文件名大小写是否一致。
- 构建产物中是否包含对应资源。
- 浏览器开发者工具的 Network 面板是否出现 404 或其他加载错误。

## 7. 与 `.isroot.in` 方案的边界

| 项目 | `.isroot.in` | `.loc.cc` |
|---|---|---|
| 网站托管 | GitHub Pages | Cloudflare Pages |
| DNS 管理 | `DNS.he.net` | `.loc.cc`  |
| 部署来源 | GitHub | GitHub 仓库 |
| 访问域名 | `hatsunemiku.isroot.in` | `hatsunemiku.loc.cc`、`hatsune-miku.loc.cc` |

两套方案相互独立。修改 `.loc.cc` 的 Cloudflare Pages 配置，不应被当成修改 `.isroot.in` 的 GitHub Pages 配置；反之亦然。
