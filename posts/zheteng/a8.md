## 1. 项目背景与最终架构

MikuFans 这个名字并不是随意取的。

它源自 Bilibili 早期使用过的名称 **Mikufans**。当年，这个名字承载着初音未来与早期 ACG 爱好者社区的记忆。后来，随着平台的发展，它逐渐成为历史。

而我一直觉得，这个名字不应该只留在过去。

因此，在最初搭建个人网站时，我便有意沿用了 **MikuFans** 这个名字。最初使用免费域名和免费托管服务，主要用于功能测试、页面设计和部署方案验证。经过一段时间的折腾，网站逐渐成形，于是购买正式域名 `mikufans.site`，让这个名字有了一个真正属于自己的落脚点。

这不是对原有平台的复刻，也不是为了延续某个商业品牌，而是一次带着个人情感的重新拾起。

**曾经属于一代人的名字，如今在这里，有了新的故事。**

网站定位是一个由歌曲、文字和回忆组成的小世界：

> **MikuFans --- A world we call ours.**
> A little world, made of songs, words and memories.

### 1.1 最终架构

| 功能 | 服务 | 用途 |
|---|---|---|
| 域名注册 | Spaceship | 注册及续费 `mikufans.site` |
| 权威 DNS | Cloudflare DNS | 管理域名解析记录 |
| 网站托管 | Cloudflare Pages | 发布静态网站 |
| 邮件收信 | Cloudflare Email Routing | 将域名邮箱收到的邮件转发至现有邮箱 |
| 邮件发信 | Resend | 使用域名身份发送邮件 |
| 缓存、安全及重定向 | Cloudflare | CDN 缓存、WAF、自定义重定向 |
| 部署后缓存清理 | GitHub Actions + Cloudflare API | Pages 部署完成后清理边缘缓存 |

### 1.2 当前网站信息

-   Pages 项目：`xxxx.pages.dev`
-   正式主域名：`mikufans.site`
-   `www` 域名：`www.mikufans.site`
-   网站为个人静态博客。

### 1.3 一个重要概念：DNS 托管切换不等于域名转入

本项目的域名注册商仍然是 **Spaceship**，只是把域名的权威 DNS Nameserver
切换到了 **Cloudflare**。

这两件事不同：

-   **切换 DNS 托管：** 域名仍在 Spaceship，DNS 记录改由 Cloudflare
    管理。
-   **转移注册商：** 将域名注册管理关系从 Spaceship 转到另一家注册商。

本手册记录的是第一种方式。没有执行注册商转移。

## 2. 购买域名

### 2.1 选择注册商并购买

本项目通过 Spaceship 注册 `mikufans.site`。

### 2.2 购买完成后先不要急着改 DNS

先在注册商控制台确认：

-   域名状态正常；
-   域名没有处于待验证或锁定异常状态；
-   能够进入 Nameserver 设置页面；
-   当前 DNS 记录已留存，特别是已有网站或邮件服务时。

如果域名此前已经有 DNS 记录，切换权威 DNS 前应先记录原有记录，避免遗漏网站、邮件或验证用途的记录。

## 3. 将 DNS 托管切换到 Cloudflare

### 3.1 在 Cloudflare 添加站点

1.  登录 Cloudflare。
2.  选择添加站点（Add a site）。
3.  输入 `mikufans.site`。
4.  选择 Free 计划。
5.  Cloudflare 会扫描并导入可识别的 DNS 记录。
6.  检查导入结果，尤其是 A、AAAA、CNAME、MX、TXT 等记录。

**注意：** DNS 扫描不保证识别全部记录。切换前必须检查记录清单，尤其不能漏掉邮件服务所需的 MX 和 TXT 记录。

### 3.2 在 Spaceship 修改 Nameserver

Cloudflare 会为站点分配两条权威 Nameserver。回到 Spaceship
的域名管理页面，将原 Nameserver 替换为 Cloudflare 提供的两条地址。

操作原则：

-   使用 Cloudflare 控制台实际显示的 Nameserver；
-   不要照抄其他域名的 Nameserver；
-   两条都要填写；
-   保存后等待注册局和递归 DNS 完成更新。


### 3.3 检查 NS 委派

可以使用 `dig` 检查：

``` bash
dig NS mikufans.site
dig +trace NS mikufans.site
```

也可以查询指定公共 DNS：

``` bash
dig @1.1.1.1 NS mikufans.site
dig @8.8.8.8 NS mikufans.site
```

检查结果应逐渐指向 Cloudflare 分配给该站点的 Nameserver。

若不同 DNS 服务器结果暂时不一致，可能是缓存和委派更新尚未完成。不要在未确认委派状态前反复修改记录。

### 3.4 配置网站 DNS 记录

本项目的主要记录如下：

| 类型 | 名称 | 目标 | 代理状态 |
|---|---|---|---|
| CNAME | `@` / `mikufans.site` | `xxxx.pages.dev` | 已代理 |
| CNAME | `www` | `xxxx.pages.dev` | 已代理 |



**注意：** 后续会通过重定向规则把 `www.mikufans.site` 统一跳转到
`mikufans.site`。保留 `www` DNS 记录是为了让该主机名能够正常接入
Cloudflare 并匹配重定向规则。

### 3.5 DNS 记录的基本用途

| 记录类型 | 常见用途 |
|---|---|
| A | 主机名指向 IPv4 地址 |
| AAAA | 主机名指向 IPv6 地址 |
| CNAME | 主机名指向另一个主机名 |
| MX | 指定邮件接收服务器 |
| TXT | SPF、DKIM、DMARC 及域名验证等文本记录 |
| SRV | 声明特定服务的主机和端口 |
| NS | 指定域名或子域的权威 DNS 服务器 |

``` text
https://mikufans.site
```

## 5. 配置 Cloudflare Email Routing 收信

### 5.1 功能定位

Cloudflare Email Routing
用于接收发往域名邮箱的邮件，并转发到已有邮箱，例如 Outlook 或 Gmail。

本项目使用它实现域名收信。它不是完整邮箱服务，不提供传统邮箱账户的收件箱，也不负责 SMTP 发信。

### 5.2 启用 Email Routing

1.  在 Cloudflare 控制台选择 `mikufans.site`。
2.  打开 Email / Email Routing。
3.  按向导设置目标转发邮箱。
4.  完成目标邮箱验证。
5.  创建自定义地址，例如 `admin@mikufans.site`。
6.  确认转发规则已启用。

### 5.3 检查邮件 DNS 记录

Email Routing 会要求配置收信相关 DNS 记录，通常涉及 MX 和 SPF 等记录。以
Cloudflare Email Routing 控制台当前给出的记录为准。

配置时特别注意：

-   不要随意删除 Email Routing 要求的 MX 记录；
-   同一个域名不要创建多条互相冲突的 SPF TXT 记录；
-   如果已有 SPF 授权，需要合并而不是简单增加第二条 SPF；
-   DKIM、DMARC 等记录应结合实际发信服务配置；
-   不要把 Resend 的发信记录误当成 Cloudflare Email Routing 的收信记录。

### 5.4 测试收信

从外部邮箱向 `admin@mikufans.site` 发送一封测试邮件，确认：

1.  发件方没有收到退信；
2.  目标邮箱收到了转发邮件；
3.  邮件没有被误判为垃圾邮件；
4.  转发地址和规则没有拼写错误。

## 6. 配置 Resend 发信

### 6.1 为什么还需要 Resend

Cloudflare Email Routing 解决的是收信转发，并不提供完整的 SMTP
发信能力。

因此，本项目使用 Resend
作为第三方邮件发送服务，通过已验证的域名发送邮件。

目标发件地址：

`admin@mikufans.site`

邮件链路可以理解为：

-   收信：外部发件人 → Cloudflare Email Routing → 已有邮箱；
-   发信：应用或程序 → Resend → 收件人的邮件服务。

### 6.2 注册并添加域名

1.  注册并登录 Resend。
2.  进入 Domains。
3.  添加 `mikufans.site`。
4.  Resend 会显示域名验证所需的 DNS 记录。
5.  在 Cloudflare DNS 中按 Resend
    控制台提供的名称、类型、内容和主机名逐条添加。
6.  等待 Resend 验证通过。

### 6.3 SPF、DKIM 与 DMARC

-   **SPF：** 声明哪些邮件发送服务有权代表域名发信。
-   **DKIM：** 通过数字签名帮助收件方验证邮件来源和完整性。
-   **DMARC：** 定义 SPF/DKIM 对齐失败时的处理策略，并提供报告机制。

配置原则：

1.  一个域名应维护一条有效的 SPF 策略，不要随意创建多条独立 SPF 记录。
2.  将需要的发信服务授权合并到同一条 SPF 策略中。
3.  按 Resend 要求添加 DKIM 记录。
4.  配置 DMARC TXT 记录，并根据实际需要选择策略。
5.  保留 Cloudflare Email Routing 的 MX 记录。
6.  添加或修改后，等待 DNS 生效，再回到 Resend 检查验证状态。

### 6.4 创建 API Key

在 Resend 的 API Keys 页面创建密钥。

本项目采用的原则：

-   使用 **Sending access**，而不是不必要的 Full access；
-   将权限限制到 `mikufans.site`；
-   密钥命名为 `Mailer`；

安全要求：

-   API Key 不要写入公开代码仓库；
-   不要放在前端 JavaScript 中；
-   不要把密钥提交到 Git；
-   使用环境变量或安全的 Secrets 管理；
-   如果密钥意外泄漏，应立即撤销并重新创建。

### 6.5 测试发信

在 Resend 控制台或受信任的后端程序中，使用已验证域名和发件地址进行测试。

检查：

-   发件人是否为 `admin@mikufans.site`；
-   收件地址是否正确；
-   Resend 是否返回成功的发送结果；
-   收件箱是否收到邮件；
-   是否进入垃圾邮件；
-   邮件头中的 SPF、DKIM、DMARC 验证结果是否符合预期。

完成以上步骤后，MikuFans 的域名发信能力即配置完成。

## 7. Cloudflare 缓存优化

站点为纯静态个人博客，内容通过 HTML 页面和独立 Markdown
文件加载，因此按资源类型设置不同 TTL，避免所有内容使用同一种缓存策略。

### 7.1 当前缓存规则

规则按顺序匹配，先匹配先生效。

#### 规则 1：静态资源长缓存

表达式：

``` text
(http.request.uri.path.extension in {"css" "js" "mjs" "woff" "woff2" "ttf" "otf" "png" "jpg" "jpeg" "gif" "webp" "avif" "svg" "ico" "mp4" "webm" "zip" "pdf"})
```

动作：

-   符合缓存条件；
-   边缘 TTL：1 个月；
-   浏览器 TTL：1 年。

适用资源包括 CSS、JavaScript、字体、图片、视频、压缩包和 PDF 等。

由于浏览器 TTL 设置较长，静态资源更新时应考虑文件版本化或清理相关缓存，避免用户继续使用旧资源。

#### 规则 2：Markdown 文档缓存

表达式：

``` text
(starts_with(http.request.uri.path, "/posts/"))
```

动作：

-   符合缓存条件；
-   边缘 TTL：1 天；
-   浏览器 TTL：遵循源站。


对当前文章目录结构而言，路径前缀规则更直接，也更容易维护。

#### 规则 3：HTML 页面短缓存

表达式：

``` text
(http.request.uri.path.extension eq "" and not starts_with(http.request.uri.path, "/admin") and not starts_with(http.request.uri.path, "/api"))
```

动作：

-   符合缓存条件；
-   边缘 TTL：2 小时；
-   浏览器 TTL：遵循源站。


### 7.2 缓存规则设计思路

| 内容类型 | 边缘 TTL | 浏览器 TTL | 设计考虑 |
|---|---|---|---|
| 静态资源 | 1 个月 | 1 年 | 资源变更频率低，优先缓存 |
| Markdown | 1 天 | 遵循源站 | 文章内容需要相对及时更新 |
| HTML | 2 小时 | 遵循源站 | 首页和页面入口适度缓存 |

### 7.3 新增动态功能时的注意事项

如果网站以后加入评论、登录、管理后台或 API：

-   不要直接沿用当前静态站点的缓存假设；
-   对需要实时变化或依赖 Cookie 的路径设置缓存排除；
-   检查缓存规则是否可能匹配动态响应；
-   当前 HTML 规则已经排除 `/admin` 和 `/api`
    前缀，新增功能时仍需重新检查规则覆盖范围。

## 8. 主域名规范化：www 301 重定向

本项目将 `mikufans.site` 作为唯一主域名，将：

`www.mikufans.site`  永久重定向到： `mikufans.site`

### 8.1 当前重定向规则

| 项目 | 当前配置 |
|---|---|
| 名称 | `www重定向根主机名` |
| 匹配表达式 | `http.host eq "www.mikufans.site"` |
| 类型 | 动态 |
| 目标表达式 | `concat("https://mikufans.site", http.request.uri.path)` |
| 状态码 | 301 |
| 保留查询字符串 | 是 |

### 8.2 为什么使用动态重定向

最初使用静态类型重定向时，出现了路径不能按预期保留的问题。

后来改为动态表达式，将原请求路径拼接到主域名之后，并启用保留查询字符串。

例如：

``` text
https://www.mikufans.site/?view=zheteng&post=a3
```

应跳转到：

``` text
https://mikufans.site/?view=zheteng&post=a3
```

这样既统一了主域名，也保留了网站依赖的查询参数路由。

### 8.3 验证

``` bash
curl -I "https://www.mikufans.site/"
curl -I "https://www.mikufans.site/?view=zheteng&post=a3"
```

检查响应中是否返回 301，以及 `Location` 是否指向 `https://mikufans.site`
并保留原路径和查询参数。

## 9. WAF 自定义安全规则

### 9.1 当前规则

规则名称：

`拦截扫描器探测`

动作：

`Block`

匹配对象为常见扫描器探测路径黑名单，包括：


该规则用于拦截针对常见 WordPress、PHP 管理入口、环境变量文件等路径的自动化探测请求。

### 9.3 观察误拦截

本项目后续待办中包含持续观察 WAF 命中情况，确认规则没有误伤正常访客。

## 10. GitHub Actions 自动清理缓存

### 10.1 为什么需要清缓存

Pages 重新部署不会自动清除 Cloudflare 已缓存的内容。

因此，如果网站更新后仍然看到旧页面或旧文章，需要考虑 Cloudflare
边缘缓存是否尚未过期。

本项目增加 GitHub Actions 工作流，在 Pages 部署成功后调用 Cloudflare API
清理缓存。

### 10.2 当前工作流信息

| 项目 | 当前配置 |
|---|---|
| 工作流文件 | `xxx` |
| 自动触发 | `deployment_status`（Pages 部署成功后） |
| API 权限 | Zone → Cache Purge → Purge |
| 作用范围 | 限定 `mikufans.site` |
| GitHub Secrets | `CF_API_TOKEN`、`CF_ZONE_ID` |

本项目已通过该工作流成功执行两次缓存清理。

### 10.3 API Token 最小权限

用于清理缓存的 Token 不需要拥有整个 Cloudflare 账户的管理权限。

建议遵循最小权限原则：

-   只授予目标 Zone 的缓存清理权限；
-   不授予 DNS 编辑、账户管理等无关权限；
-   将 Token 存放在 GitHub Actions Secrets；
-   不要将 Token 明文写进工作流文件；
-   如果 Token 曾经暴露，及时撤销并重新创建。

### 10.4 手动清理缓存

如果自动工作流未触发，也可以在 Cloudflare 控制台手动清理：

1.  打开 `mikufans.site` 对应站点；
2.  进入缓存配置；
3.  根据实际情况选择清除全部缓存或按 URL 清除。

对于只更新了文章的情况，可以优先考虑清除对应文章 URL，避免不必要地清除全部静态资源缓存。

### 11.3 查看缓存状态

``` bash
curl -I https://mikufans.site/
curl -I https://mikufans.site/posts/zheteng/a3.md
```

重点观察响应头中的 `CF-Cache-Status` 等信息。常见状态包括：

-   `HIT`：缓存命中；
-   `MISS`：未命中，需要从源站获取；
-   `BYPASS`：按规则绕过缓存；
-   `DYNAMIC`：该响应未按普通静态缓存方式处理；
-   `EXPIRED`：缓存已过期，需要重新获取。

实际状态应结合响应头、Cloudflare 分析数据和规则匹配情况判断，不能仅凭一次请求下结论。


### 11.4 发版后的标准检查流程

每次网站更新后：

1.  确认 GitHub Pages 部署成功；
2.  检查 Actions 是否触发缓存清理；
3.  如果自动清理失败，查看工作流日志；
4.  必要时在 Cloudflare 手动清理缓存；
5.  访问首页和刚更新的 Markdown 文章；
6.  检查页面、图片、字体和文章内容是否正常；
7.  使用 `curl -I` 检查状态码、重定向和缓存响应头。

### 11.5 更新延迟参考

按当前配置估算：

| 内容 | 边缘 TTL | 更新注意事项 |
|---|---|---|
| 静态资源 | 1 个月 | 更新后应清理缓存；浏览器 TTL 为 1 年 |
| Markdown | 1 天 | 更新后可按 URL 清理 |
| HTML | 2 小时 | 未主动清理时，边缘缓存可能在 TTL 到期后更新 |

这里的 TTL 是缓存有效期设置，不代表所有访客一定会在该时间点同时看到更新。浏览器本地缓存、边缘缓存和部署传播都可能影响实际体验。

## 附录 A：重要安全提醒

1.  **不要公开 API Token、API Key、账户凭据或私有密钥。**
2.  DNS 截图或配置文档对外分享前，应检查是否包含账户 ID、Zone
    ID、内部标识或邮箱地址。

5.  WAF 规则应根据真实业务路径维护，避免误拦截。
6.  缓存规则适用于当前静态网站架构；网站加入动态功能后必须重新评估。
7.  Resend 的 DNS 验证值和 API 权限以服务商当前控制台为准。
